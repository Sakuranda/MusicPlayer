## 1. 环境概览

| 项 | 值 |
|---|---|
| 服务器 | Debian 12 x86_64，8 vCPU / 8GB / 30GB 磁盘 |
| SSH | `ssh hk`（~/.ssh/config，密钥 `id_ed25519_hk`，端口 63195） |
| 部署目录 | `/opt/musicplayer`（Git 仓库 + docker compose） |
| Docker | 29.x + Compose v5 |
| 容器 | `musicplayer-api`（FastAPI+网页，8080）、`musicplayer-navidrome`（Subsonic，4533） |
| 系统级 Caddy | 反代 `music.sakuranda.site` → 127.0.0.1:8080（自动 HTTPS） |

下载相关环境变量位于 `deploy/.env`：`DOWNLOAD_THREADS` 是整个 API 服务共享的
下载并发（默认 3，代码硬限制 1–5）；`METADATA_THREADS` 控制解析详情的工作线程；
`BILI_API_INTERVAL` 控制所有 B 站 JSON API 请求之间的最小间隔，数据中心 IP 建议保持 0.5 秒或更高。
`LYRICS_API_INTERVAL` 控制三个歌词服务共享的请求间隔（默认 0.35 秒），避免大收藏夹产生请求尖峰。
已保存收藏夹的每日更新由 API 容器内的轻量调度线程完成，无需额外 cron；容器重启后会立即检查到期项，随后每 15 分钟扫描一次。每个收藏夹以数据库中的 `last_checked_at` 保证至少间隔 24 小时。
网页登录由 `ADMIN_USERNAME`、`ADMIN_PASSWORD` 启用；`AUTH_SECRET` 用于签名 HttpOnly 会话 Cookie，
必须使用独立随机值。`API_TOKEN` 继续供运维脚本和应急 API 调用，不再要求普通网页用户填写。
`docker-compose.yml` 通过可选 `env_file` 直接加载该文件；不要另建项目根目录 `.env`，也不要把这些变量
重复写进 compose 的 `environment`，否则显式空值/默认值会覆盖部署配置。

## 2. 首次部署

```bash
# 前置：本机已配好 ssh hk 免密登录
./deploy/deploy.sh
```

脚本做的事：`git clone`（或 pull）到 `/opt/musicplayer` → 生成 `deploy/.env`（含随机 API_TOKEN、管理员密码和会话签名密钥）→ `docker compose up -d --build`。首次生成的管理员密码只显示一次，应立即保存。

手动等价步骤：

```bash
ssh hk
git clone https://github.com/Sakuranda/MusicPlayer.git /opt/musicplayer
cd /opt/musicplayer
cp deploy/.env.example deploy/.env
# 编辑 .env 设置 ADMIN_USERNAME / ADMIN_PASSWORD
# API_TOKEN 用 openssl rand -hex 16，AUTH_SECRET 用 openssl rand -hex 32 生成
docker compose up -d --build
```

首次使用还需创建 Navidrome 账号（见[第 5 节](#5-navidrome-管理)）。

## 3. 更新代码

```bash
cd /opt/musicplayer && git pull --ff-only && docker compose up -d --build
```

或本地：

```bash
ssh hk 'cd /opt/musicplayer && git pull --ff-only && docker compose up -d --build'
```

> ⚠️ 注意：重建容器会中断正在进行的下载任务（几秒钟）。用户正在使用时先沟通；前端只会对曲库读取等幂等请求自动重试 502，导入/删除等写操作不会盲目重放。服务重启后会自动把中断项标成错误，避免永久卡在「下载中」；重新导入即可重试。旧版本数据库可手动复位：
>
> ```bash
> docker exec musicplayer-api python -c "
> import sqlite3
> c = sqlite3.connect('/data/musicplayer.db')
> c.execute(\"UPDATE songs SET status='pending', error=NULL WHERE status='downloading'\")
> c.commit()"
> ```

## 4. 域名与 HTTPS（Caddy）

服务器上运行的是**系统级 Caddy v2**（非 compose 内的 caddy 服务）：

```bash
systemctl status caddy          # 服务状态
cat /etc/caddy/Caddyfile        # 主配置（yxai 站点等）
ls /etc/caddy/sites-enabled/    # 站点配置（music.sakuranda.site.caddy 等）
caddy validate --config /etc/caddy/Caddyfile   # 改配置后先校验
systemctl reload caddy          # 重载
```

- `music.sakuranda.site` → 反代 127.0.0.1:8080（本项目的网页+API）
- 新增子域名：在 `sites-enabled/` 加配置文件（参考 `music.sakuranda.site.caddy`），需先在 Cloudflare 加 A 记录 → 45.125.33.88，Caddy 自动签发证书
- 给 iOS 上 HTTPS：加 `navi.music.sakuranda.site` → `reverse_proxy 127.0.0.1:4533`，Amperfy 填 `https://navi.music.sakuranda.site`

docker-compose 里的 `caddy`（profile https）是备用方案，当前未启用。

## 5. Navidrome 管理

- **管理后台**：`http://45.125.33.88:4533`（网页登录后右上角设置）
- **创建首个管理员**（无管理员时）：

```bash
ssh hk 'curl -X POST http://localhost:4533/auth/createAdmin \
  -H "Content-Type: application/json" \
  -d "{\"username\":\"YOUR_NAME\",\"password\":\"YOUR_PASS\"}"'
```

- 改密码/多用户：Navidrome 网页 UI
- 曲库扫描：自动（文件监听 + 启动扫描），无需手动干预
- 配置：compose 中的 `ND_*` 环境变量

## 6. 数据目录与备份

```
/opt/musicplayer/
├── docker-compose.yml
├── deploy/.env            # 管理账户、AUTH_SECRET、API_TOKEN 等配置（不提交 Git）
└── data/                  # 挂载进 api 容器 /data
    ├── musicplayer.db     # SQLite：任务 + 歌曲（WAL 模式，含B站链接/分P/歌词）
    ├── music/             # 曲库（原始 AAC/M4A，不二次编码；同名 .lrc）
    ├── covers/            # 320px 低质量 JPEG 封面缓存（bvid.jpg）
    ├── cookies/           # 用户粘贴的 B 站 Cookie（Netscape 格式）
    └── navidrome/         # Navidrome 数据库与缓存
```

**在线备份**（先用 SQLite backup API 生成一致快照，再连同音乐打包）：

```bash
ssh hk 'docker exec musicplayer-api python -c "import sqlite3; s=sqlite3.connect(\"/data/musicplayer.db\"); d=sqlite3.connect(\"/data/musicplayer-backup.db\"); s.backup(d); d.close(); s.close()" && cd /opt/musicplayer && tar czf /root/musicplayer-backup-$(date +%F-%H%M%S).tar.gz data/musicplayer-backup.db data/music && rm data/musicplayer-backup.db'
```

**恢复**：解压回 `data/` 后 `docker compose restart`。

API 进程使用 SQLite WAL 模式，每个工作线程持有独立连接，写锁最多等待 30 秒。不要在服务运行时只复制
`musicplayer.db` 主文件，因为尚未 checkpoint 的数据可能仍在 `-wal` 文件；上面的在线备份命令会生成一致快照。

CSV 清单导出：「设置」页按钮或：

```bash
curl -o songs.csv "http://45.125.33.88:8080/api/export.csv?token=YOUR_TOKEN"
```

## 7. 日志与排障

```bash
docker logs musicplayer-api --tail 100        # 后端（含下载错误）
docker logs musicplayer-navidrome --tail 100
journalctl -u caddy -n 50                     # Caddy（证书/502）
docker stats                                  # 资源占用
df -h /                                       # 磁盘（注意 30G 上限）
```

常见问题：

| 症状 | 排查 |
|---|---|
| 网页 502 | api 容器在重启？`docker ps` + `docker logs` |
| 下载 412 / bad parameter | B 站风控，已内置重试；持续出现检查服务器出口 IP 是否被重点风控 |
| 重复导入开始下载旧歌 | 新版会以真实文件和分P去重；先确认部署版本，再检查 `file_path` 对应文件是否确实存在 |
| 磁盘满 | `du -sh /opt/musicplayer/data/*`，删除不需要的歌或清理 covers |
| Navidrome 无新歌 | 检查 `data/music` 挂载；等 10 秒文件监听触发；或 Navidrome 后台手动扫描 |
| 登录验证码不显示 | 检查 `/api/auth/captcha` 与容器日志；确认 ADMIN_USERNAME/ADMIN_PASSWORD 均已设置 |
| 登录后立即失效 | 检查 AUTH_SECRET 是否在重建容器时被改动；HTTPS 反代应传递 X-Forwarded-Proto |

## 8. 旧系统数据迁移

旧版 Music Player（compose 项目 `sakuranda-music`）已停止但数据保留：

- 音乐文件：`/opt/sakuranda-music/data/music/`
- 数据库：`/opt/sakuranda-music/data/`（postgres）

迁移旧歌曲到新系统：把音频文件复制进 `/opt/musicplayer/data/music/<专辑>/`，Navidrome 会自动扫到。网页曲库只显示经本系统导入的歌，旧歌如需在网页出现需重新导入对应收藏夹（去重机制会复用已存在的文件……若旧文件直接复制进来，重新导入该视频时会跳过下载、直接关联）。

### 修复历史 DASH 音频封装

B 站 DASH 直连文件可能含 `moof` 分片且头部时长为零。下载入库前现在使用 FFmpeg `-c:a copy -movflags +faststart` 无损重封装为普通 M4A，逐个比较压缩音频包 SHA-256，保留标签、封面、歌词，成功后原子替换。不会重新编码音轨。曲库时长改为读取实际文件，避免多 P 总时长误用。

历史文件先检查，再执行（确认无下载任务）：

```bash
docker exec musicplayer-api python -m scripts.repair_media
docker exec musicplayer-api python -m scripts.repair_media --apply
```

执行时在 `/data/backups/media-时间戳/` 保存 SQLite 快照与原媒体硬链接，失败保留原文件；不修改歌曲 ID、路径和歌单关系。备份需人工确认正常后再清理。回滚时从该目录原样复制对应媒体回曲库；若期间有其他业务写入，只恢复对应歌曲的时长，不直接覆盖整个数据库。
